# 浮動視窗直接記錄下一組 — PRD

## 背景與目標

浮動視窗（F64→F89→F100）存在的前提是「**你人不在 app 裡**」——在健身房滑手機、聽音樂、回訊息時，倒數要跟著你。但它目前只能看與控制倒數；真要記下一組，還是得回 app。

這條要補完那個閉環：**在視窗裡直接記完這組，然後開始下一輪休息**，中途不必回 app。休息結束的下一個動作永遠是「記下這組」，讓它就地完成才是這個視窗該長的樣子。

Ryan 2026-07-31 提案並定調：**重量與次數可調**（不做唯讀版）。理由見「關鍵決策一」。

vault 對應：`projects/2026-07-健身紀錄系統/`。

## 非目標（本次不做）

- 不在視窗裡選累度（RPE）——五個停點塞不進 214dp，且累度是回顧用的，補記於 app 內即可（記錄時預設沿用上一組的值）
- 不在視窗裡換動作、不顯示已完成的組列表、不做編輯或刪除
- 不做臨時加動作
- 不改 app 內 logger 的任何行為
- 不做離線時的原生端佇列（見「關鍵決策二」：離線由既有的前端佇列處理）

## 關鍵決策

### 一：重量與次數**可調**，不是唯讀

唯讀版只在「下一組跟上一組完全一樣」時有用。真實訓練裡加重、掉次數都很常見，唯讀等於使用者每次都要先判斷「這次能不能在視窗做」——**規則不確定比功能少更糟**。所以給 ± 兩顆，代價是展開態變高（見「版面」）。

### 二：記錄邏輯**只有一份**，原生不重寫

記一組不是「打一個 API」那麼單純，它還牽涉：離線佇列（`js/queue.js`）、組號遞增（F32 的 `nextSetNumber`）、樂觀更新與同步狀態、`client_uuid` 去重。這整套在前端 JS。

原生若自己打 API，等於把上面每一項都再實作一次；兩份實作遲早會走鐘，而**走鐘的是訓練資料本身**。所以：

> **浮動視窗只負責「回報使用者按了什麼」，實際記錄一律由前端 JS 執行。**

這與 F71 ⑥（暫停／繼續／停止的回報）是同一個架構，不是新發明的東西。

風險是 app 在背景時 WebView 被節流／被系統回收，JS 可能不在。**這是本 feature 唯一的技術風險**，處理方式見 R4。

## 名詞定義

- **待記組**：視窗上顯示的重量與次數，＝這一輪休息結束後要記的那一組。初值為前端在開始這輪休息時送下來的值（通常是剛記完那組的重量與次數）
- **就地記錄**：使用者在視窗按下「記下這組」，前端完成寫入，視窗自動接著開始下一輪休息

## 需求與驗收標準

### R1：作為使用者，我想在浮動視窗看到下一組要做的重量與次數

- Given 這輪休息由 app 發起，且浮動視窗顯示中
- When 視窗處於展開態
- Then 動作提示那一行下方顯示「待記組」：`{重量} kg × {次數}`，Mono 字體、數字用 tabular-nums
- Given 動作是自體重動作（`is_bodyweight`）
- When 顯示待記組
- Then 重量顯示為「自體重」或「+{重量} kg」（與 app 內 logger 的「負重 KG」一致）
- Given 視窗處於收合態（76dp 圓）
- When 顯示
- Then **不顯示**待記組——收合態只有圓環與秒數，這條不改 F89 ①

### R2：作為使用者，我想直接在視窗調整重量與次數

- Given 視窗展開且顯示待記組
- When 按重量的 −／＋
- Then 重量以 2.5 kg 為級距增減，下限 0；顯示即時更新
- When 按次數的 −／＋
- Then 次數以 1 為級距增減，下限 1
- Given 觸控目標
- Then 每顆 ≥48dp、彼此間距 ≥8dp（F74／F89 ⑦ 不放寬）
- Given 調整只在視窗內
- Then **不立即寫入**任何地方——它只是還沒送出的草稿，與 app 內步進器同一個分寸

### R3：作為使用者，我想按一下就記完這組並開始下一輪休息

- Given 視窗顯示待記組
- When 按下主按鈕「記下這組」
- Then 依序發生：① 前端寫入這一組（走既有記錄路徑，含離線佇列）② 這輪休息結束 ③ 依該動作的參考休息**開始新的一輪倒數** ④ 視窗上的待記組更新為剛記的值、組號 +1
- Given 記錄成功
- Then 視窗給一次明確的成功回饋（不是靜默切換——使用者要知道那一下真的記進去了）
- Given app 內同時開著 logger
- When 就地記錄完成
- Then app 內的組列表與組號跟著更新，兩邊不得各說各話

### R4：作為使用者，我想在就地記錄失敗時**明確知道**，而不是以為記好了

這條是本 feature 的核心風險，不可省略。

- Given app 程序已被系統回收，或 WebView 無回應
- When 按下「記下這組」且在 3 秒內沒有收到前端的成功回報
- Then 視窗顯示明確的失敗狀態（文案指出「沒記到」與下一步），**不得**表現得像記錄成功、**不得**靜默吞掉
- Then 主按鈕退回「回 app 記下一組」，讓使用者走原本那條路
- Given 記錄失敗
- Then **不開始新的一輪休息**——休息開始了但組沒記到，是最糟的組合（人以為記完了，資料卻缺一筆）
- Given 裝置離線但 app 程序活著
- When 就地記錄
- Then 照常成功（進前端的離線佇列），**不視為失敗**——離線是既有能力，不是這條的例外

### R5：作為使用者，我想「回 app 記下一組」這條路仍然存在

- Given 視窗顯示待記組
- Then 仍有一個入口能拉起 app 到 logger（F89 ④ 不回歸）
- Given 就地記錄可用
- Then 主按鈕是「記下這組」，「回 app」退居次要位置（不並列成兩顆同等大小的主按鈕——那會讓人每次都要選）

### R6：不回歸

- F69（app 前景且在計時頁面就藏視窗）、F72（歸零後往上數、三條停止路徑）、F73（鬧鈴響時停止鈕警示色）、F89 ⑤（點本體收合⇄展開、拖曳移動與位置持久化）、F89 ⑧（所有碰 view 的進入點經 onMain）、F100（停止＝停響並歸位、✕ 才消失）
- F32：組號仍以「該動作在本次訓練的最大組號 +1」計算，不得因為記錄來源不同而走另一套

## 版面

展開態由 214×214dp 長高到約 280dp：

```
┌──────────────────────────┐
│ ▬  LIFT·LOG           ✕ │
│         ◯ 1:23           │   126dp 圓環
│      槓鈴臥推 · 第 3 組    │
│  −   40 kg   ＋           │   ← R2 新增
│  −    5 次   ＋           │   ← R2 新增
│  ⏸    停止   −15s  +15s   │
│      記下這組              │   ← R3（--accent）
│      回 app（次要）        │   ← R5
└──────────────────────────┘
```

秒數與待記組並存時資訊密度偏高，實作時若超出可用高度，優先壓縮控制鈕列的間距，**不得**壓觸控目標（F74）。

## 開放問題（實作前要有答案）

1. **喚醒 WebView 的可靠度**：app 在背景多久之後 JS 就叫不動了？要先在真機上量，量到的數字決定 R4 的 3 秒門檻合不合理
2. **成功回饋的形式**：視窗閃一下、震動、還是文字？震動在健身房最有感但可能與鬧鈴混淆
3. **累度**：就地記錄的組沿用上一組的累度值，這對回顧的意義有多大損失？（Ryan 判斷）
