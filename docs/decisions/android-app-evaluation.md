# 決策文件：lift-log 是否／如何做成 Android app

- **日期**：2026-07-20（2026-07-27 更新狀態）
- **狀態**：**已決議 —— 走方案 B（Capacitor），做到階段 4（浮動視窗）**。Ryan 於 2026/07/27 拍板，已拆成 `feature_list.json` 的 F61–F64。§5 的四個未決事項處置：①做到階段 4 ②散佈採 sideload ③建置環境待安裝，步驟見 `docs/android-build-setup.md` ④採建議做法——app 版走本機通知、web 版續用 F31 Web Push。vault 側決策紀錄為 D6
- **背景**：lift-log 目前是自架 PWA（FastAPI 後端＋原生 JS 前端＋Service Worker，經 Cloudflare Tunnel 對外）。F31 剛做完 Web Push 休息通知。使用者主力在 Android。
- **決策問題**：要不要把 lift-log 做成 Android app？若要，走哪條路、範圍多大？

---

## 1. 動機（為什麼會想變 app）

對照使用者實際痛點，逐一看哪些是「變 app」才解得掉：

| 痛點 | 現在（PWA） | 變 app 後 |
|---|---|---|
| **浮動時鐘**（休息倒數浮在別的 app 上） | ❌ 手機網頁做不到（原生專屬） | 只有**原生 overlay**（`SYSTEM_ALERT_WINDOW`）能做，需自寫 native |
| **休息通知可靠度** | ⚠️ 靠 Web Push：伺服器排程、重啟會漏、省電模式可能擋 | ✅ **原生本機通知**：手機端排程、準時、**不用伺服器、離線／關 app 都行** |
| **每次要清快取才更新** | 😖 SW 快取常需手動清（見 F14/F24 的一次性 bootstrap） | ✅ 任何打包方式都解決，改用 app 更新 |
| **像真的 app／主畫面圖示** | 半套（PWA 可加主畫面） | ✅ 真 app、可上架 |

**關鍵洞察**：F31 的 Web Push 是「純網頁」的正解；一旦變原生，**本機通知會直接取代它且更好**（不用伺服器、離線可用、修掉「伺服器重啟漏通知」的限制）。F31 的投資不算白費——它是 web 版的正確解，原生版是升級。

---

## 2. 方案評估

| 方案 | 做法 | 解鎖什麼 | 沿用現有碼 | 工作量 |
|---|---|---|---|---|
| **A. TWA**（Trusted Web Activity） | Bubblewrap／PWABuilder 把 PWA 包成 APK（底層仍是 Chrome） | 主畫面 app、可上 Play Store、**免快取更新煩惱** | 100% | **低**（1–2 天） |
| **B. Capacitor**（推薦） | 前端裝進原生 WebView＋JS↔原生橋接，可加原生 plugin | A 全部 **＋ 原生本機通知、前景服務倒數、可做浮動視窗** | ~100% 前端 | **中**（分階段） |
| **C. 全原生**（Kotlin＋Compose） | UI 全部重寫 | 全部、效能最佳、最完整 | 只剩後端 | **高**（數週） |
| **D. React Native／Flutter** | UI 用 RN/Flutter 重寫 | 全部＋跨 iOS | 只剩後端 | **高**（數週） |

### 各方案要點

- **A. TWA**：最便宜的「變成 app／可上架」，但底層仍是 Chrome → **web 的限制照舊**（背景計時、無浮動視窗、通知可靠度同 PWA）。**不解決浮動時鐘**，也不比 PWA 多解通知問題。適合「只想要主畫面 app＋免清快取」。
- **B. Capacitor**：甜蜜點。保留整套 web UI，包成原生殼，再**漸進**加原生 plugin。能拿到原生本機通知、前景服務、（自寫）浮動視窗。後端不動、前端幾乎不動。
- **C. 全原生**：把剛做好的所有畫面重寫，對個人工具是過度投資。除非要做成商用級 app。
- **D. RN／Flutter**：同樣要重寫 UI；只有在「想要 iOS＋Android 都原生且願意重寫」時才考慮。

## 3. 建議方案：Capacitor，分階段（隨時可停）

> 理由：個人單人工具、前端已是成熟 PWA、主要想要的是「可靠通知」與「免更新煩惱」（可選再加浮動時鐘）。Capacitor 讓現有碼幾乎 100% 沿用，並可逐步解鎖原生能力，**web 版與 app 版共用同一前端＋後端**。

| 階段 | 內容 | 解決什麼 | 工作量 |
|---|---|---|---|
| **1** | Capacitor 包起來 → 真 APK、主畫面 app | 免清快取、真 app | 低（~1–2 天） |
| **2** | 休息計時器改用**原生本機通知**（`@capacitor/local-notifications`，手機端排程） | 通知可靠度大躍進、可拿掉伺服器推播複雜度 | 低–中（~1 天） |
| **3**（選配） | **前景服務＋常駐倒數通知**（通知列即時顯示剩幾秒） | 「不開 app 也看得到時間」的實務版 | 中（~2–4 天，native Kotlin） |
| **4**（選配） | **真・浮動視窗**（自寫 overlay plugin，`SYSTEM_ALERT_WINDOW`） | 最初想要的浮動時鐘 | 中–高（~3–5 天，native Kotlin） |

**多數情況做到階段 2 或 3 就完全滿足**（可靠通知＋通知列看倒數）。階段 4 的浮動視窗是錦上添花但工程最重、且權限／上架較麻煩。

## 4. 現實考量與風險

- **後端完全不用動**（A/B）：FastAPI 遠端照舊，app 打現有 API（已經是這樣）。
- **散佈方式**：
  - **自己 sideload APK**＝免費、立即、不用 Play Store——個人用足夠。
  - **Play Store**＝開發者帳號 US$25（一次）＋簽章＋商店審查；只在想輕鬆安裝/更新或分享時才需要。
- **簽章金鑰（keystore）**：要產生並妥善保管（遺失無法更新同一 app）。
- **建置環境**：需 Android Studio／Gradle（現行 Windows dev box 應未安裝）；建置那步可能要在本機跑或另外設定。
- **iOS 之後想做**：Capacitor 跨平台、門開著；TWA 只有 Android。
- **維護成本**：Capacitor 多一個建置步驟與 native 專案（Android Studio/Gradle），比純 PWA 稍重；TWA 較輕。
- **浮動視窗現實**：即使原生，`SYSTEM_ALERT_WINDOW` 要使用者在設定裡手動授權，Google 對它審查嚴（Play Store 要充分理由）。sideload 個人用沒問題。**先做「前景服務常駐倒數通知」通常就夠**，比真 overlay 省事且不惹審查。
- **雙軌並存**：導入 Capacitor 後，web 版（PWA）可繼續存在，兩者共用同一前端＋後端；不是二選一。

## 附錄：F31（Web Push）與原生本機通知的關係

| | F31 Web Push（現況，web） | 原生本機通知（階段 2） |
|---|---|---|
| 排程在哪 | 伺服器（in-process asyncio） | 手機端 OS |
| 需要伺服器 | 是 | 否 |
| 伺服器重啟 | 會漏當下未觸發的通知 | 不受影響 |
| 離線／關 app | 依賴推播服務送達 | 照常觸發 |
| 平台 | Android Chrome 佳、iPhone 需加主畫面 | 原生 app 一致可靠 |
| 適用 | 純網頁版的正解 | app 版的更優解 |

→ 變 app 後，app 版走本機通知、web 版續用 F31，各取所長。
