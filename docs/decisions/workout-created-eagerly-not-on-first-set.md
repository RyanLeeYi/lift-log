# workout 在「按開始訓練」時建立，不是「記第一組」時

> 2026-07-30，F92 ⑦。簽核時定案。

## 決策

維持現行時機：按「開始訓練」就 `POST /api/workouts` 建立。
**不改成「記第一組才建立」**，改用「離開時沒記東西就刪掉」（F92 ⑥）來防止空 workout 堆積。

## 為什麼不延後建立

延後建立看起來更乾淨（不產生空 workout），但會弄壞一條真實路徑：

**線上按「開始訓練」→ 走進健身房地下室失去訊號 → 記第一組。**

延後建立的話，第一組要記的當下沒有 workout 可掛，而離線也建不出來
（離線佇列的每一筆都以 `workout_id` 為 key）。現行做法在按開始的當下就把 workout 拿到手，
之後整場離線都能記。

反過來說，現行做法**本來就不支援「離線開始訓練」**（`startWorkout` 會 await `createWorkout`，
離線直接失敗）。所以延後建立並不會換到「離線可開始」這個好處，只是把可離線的範圍變窄。

## 代價（知道且接受）

app 被系統回收、或分頁直接關掉而沒按「結束訓練」時，空 workout 仍會留在資料庫。
兩件事讓它不造成可見問題：

- **F90** 會在下次開啟時**續接**那場，而不是另建一場——所以不會愈積愈多
- **F92 ①–④** 讓沒有有效組的 workout 在日曆與本週進度一律不顯示
