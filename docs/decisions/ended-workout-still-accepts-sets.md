# 已結束的 workout 仍接受寫入 sets

> 2026-07-30，F91 ⑥。簽核時定案。

## 決策

`POST /api/workouts/{id}/sets` **不檢查 `ended_at`**。已結束的訓練照樣可以寫入組，不回 409。

`ended_at` 只影響一件事：**前端還原時能不能續接這場訓練**（`confirmActiveWorkout()`）。

## 為什麼不擋

直覺會說「結束了就該拒絕寫入，否則這個欄位形同虛設」。但擋下來會踩到離線佇列：

1. 在健身房離線記了 3 組 → 進 IndexedDB 佇列等補傳
2. 回家用網頁版按「結束訓練」→ 伺服器記下 `ended_at`
3. 手機一連上網補傳 → 若伺服器回 409，`flushQueue` 會把它們標成 **failed**（永久性 4xx 不重試）
4. 使用者只剩「手動捨棄」一條路 → **那 3 組真的沒了**

而 F91 要解的問題是**續接**，不是寫入——B 裝置不該把已結束的訓練接下去。
擋寫入沒有解決那個問題，只是額外製造了資料遺失的路徑。

## 代價（知道且接受）

- 已結束的訓練仍可能被寫入新組（例如另一台裝置正停在 logger 畫面沒重整）。
  發生時資料本身是對的（組確實是那天練的），只是「結束時間」之後還有組。
- 因此 `ended_at` **不是**「這場訓練最後一組的時間」，不能拿來算訓練時長。要算時長得用 sets 的時間。
