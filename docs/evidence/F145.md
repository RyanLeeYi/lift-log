## 做了什麼

server 端的衝突契約在 F143 就完成（`_conflict` 回 `reason` ＋ server 實體），F144 讓 Android
把 push 回來的衝突落地到 `sync_conflicts`。本條補的是**中間那段：列出來、讓人選、把選擇變成
新的 mutation**。

- `LocalStore.conflicts()`：未解決衝突清單，每筆同時帶 `local` 與 `server` 兩份值。
- `LocalStore.resolveConflict(conflictId, choice, mutationId)`：
  - `local`（保留本機）＝欄位用本機的、版本與時間用 server 的，重排成新的 versioned mutation
    （`base_version` 對齊 server version），所以重送不會再撞同一個 `version_mismatch`。
  - `server`（採用雲端）＝套用雲端值（tombstone 則套用刪除），丟棄被拒的 mutation。
  - 雲端已刪除時**拒絕**「保留本機」——那等於讓刪掉的資料復活，PRD R4 明文禁止。
  - 解完若沒有其他失敗 mutation，順手清掉 `last_error_code`，否則同步狀態會永遠卡在「錯誤」。
- `SyncPlugin` 兩個橋接方法；`native-sync.js` 的 `readNativeConflicts` / `resolveNativeConflict`
  （只接受明確的 `local` / `server`，不做任何自動判定）。
- 設定頁衝突收件匣：**兩邊的值一定同時畫出來**。只說「有衝突」等於逼人猜。

## 未改 passing 的理由（要 Ryan 裁決）

acceptance 第 9 條：「衝突情境以 **Android ↔ Web** 為準，兩端 contract tests 全綠」。

- **字面讀**：兩端各自的 contract test 全綠 → 已達成（Python `test_sync_contract.py` ＋ Android
  `SyncContractFixtureTest` 跑同一組 `tests/fixtures/sync/*.json`）。
- **嚴格讀**：真的用 Web 改一筆、讓 Android 推送撞上衝突 → **現在做不到**。Web 的 REST 寫入
  還沒進 sync change log，那條整合排在 **F146**。

驗收者自己判 pass，但在報告裡明講它是用第一種讀法。**讓驗收者放寬凍結 acceptance 來換一個
pass，跟直接改 acceptance 是同一件事**，所以這裡不自動改 passing。

兩條路，擇一（Ryan 決定）：

1. 認第一種讀法 → 現在就改 passing，並把 acceptance 措辭改成「雙端 schema contract tests 全綠」
   重新簽核（規格變更要記原因）。
2. 認第二種讀法 → 維持 failing，等 F146 把 Web 寫入接進 change log 後，補一條真正的
   Android ↔ Web 端對端情境再驗。

## 規格回饋（驗收者提出，值得收）

- 「附 server 版本與 **client mutation**」：server response 其實只回 `server`，client mutation
  是靠 Android 端 `sync_outbox` 保留（只標 `error_code` 不刪）達成。行為符合意圖，但字面與
  PRD 的介面契約範例對不起來，建議規格註明「client mutation 由呼叫端自留」。
- `app.js` 全域耦合 `document`，前端顯示條件無法用 node 直接驗；要能自動驗收就得把
  `isNativeApp() && conflictItems.length > 0` 抽成不依賴 DOM 的純函式。
