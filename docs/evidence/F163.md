# F163 evidence：內建對話的 tool 橋接層

2026-08-22 實作（dispatch session）。簽核來源：agent-brief 收件匣回覆「簽核三條」。

## 做了什麼

`app/mcp.py` 新增 in-process 入口 `run_tool(mcp, user_id, name, arguments)`：

- 身分靠 `ContextVar _INPROCESS_USER_ID`，在 `domain_session()` 內**優先於** access token
  與 legacy fallback。少了這個優先序，登入中的 web/app 使用者會落回 legacy 共用 DB
  （`get_access_token()` 在 in-process 一律回 None，這正是 acceptance 開頭描述的災難）。
- user → data DB 的解析抽成 module-level `_user_session()`，`/mcp` 那條路與橋接層共用
  同一段 F147 路徑推導，沒有第二套。
- tool 表**就是** `/mcp` 那份：`run_tool` 呼叫同一顆 FastMCP 實例的 `call_tool`，
  沒有為內建對話另建 tool、也沒有第二條寫入路徑。
- `log_workout` 新增選填 `dry_run`（④）。dispatch 方式與 `app/api/workouts.py` 相同
  （`dry_run_log_workout` vs `log_workout`）——**沒有改 `workouts_svc.log_workout` 的簽名**，
  那是停止條件明列不得擅動的共用契約。acceptance ④ 字面寫「原樣傳給 log_workout」，
  實作改為原樣傳進 `LogWorkoutIn.dry_run` 再由入口分派，行為相同。
