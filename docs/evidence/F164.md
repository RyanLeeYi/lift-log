# F164 evidence：/api/chat 與 LLM key 來源

2026-08-22 實作（dispatch session）。**拍板紀錄**：agent-brief 收件匣回覆「F164 採 (a) server 代打」
——自填 key 由 client 每次請求以 `X-LLM-API-Key` 夾帶，server 代打上游，key 不落地、不進 log。

## 做了什麼

- `app/api/chat.py`（新檔）：`POST /api/chat/`。auth 走既有 `require_domain_auth`；
  legacy scope 一律 403（①）。
- tool 呼叫全部經 F163 的 `run_tool`，綁 `request.state.domain_scope`（＝呼叫者 user id）；
  請求 body 沒有任何身分或 DB 欄位可指定（②）。
- 兩段式寫入（③）：LLM 回 `tool_use` 且是寫入類 tool 時，只跑 `dry_run=True`，
  回 `pending_write` ＋ F152 摘要就結束；真正寫入只發生在 client 帶回 `pending_write`
  的第二次請求，**那條路徑完全不呼叫 LLM**（確認的是使用者，不是模型），
  且只接受寫入類 tool（否則它會變成繞過 LLM 的任意 tool 呼叫器）。
- key 來源（④⑤）：header 自填優先，其次 `.env` 的 `LIFTLOG_LLM_API_KEY`；
  兩者皆無回 400 `{"error": "llm_key_missing"}`。
- 上游用既有 `httpx`（⑥），無新依賴；model／base URL／timeout 可由 `.env` 設定，
  預設 Anthropic Messages API。401/403→`llm_unauthorized`(502)、429→`llm_rate_limited`(429)、
  逾時→`llm_timeout`(504)；回應只帶錯誤碼，不含 key 也不含上游 body。
- 單輪（⑦）：不存歷史、不建資料表；每次請求的 messages 只有這一句。
