# F154 — domain 表與同步層合一

實作日：2026-08-14。決策依據：vault `DECISIONS.md` **D17**（Ryan 於 grill 十題裁決 Q1／Q6／Q8～Q10）。

## 問題（做 F146 時查出來的）

`app/services/sync.py` 從頭到尾沒碰過 domain models，domain 表也沒有 `sync_id`／`version`。
同一個 user 的 data DB 裡是**兩份互不相干的資料**：Android 同步上來的在 `sync_entities`，
REST／MCP 讀寫的在 domain 表。手機記的組網頁查不到，網頁記的手機同步不到——而兩邊各自的
單元測試都會過。PRD R5／R6 早就寫了「同一份 change log」「不得有繞過同步版本的第二條寫入路徑」。

## 做了什麼

**schema**（`DOMAIN_SCHEMA_VERSION` 3 → 4，既有 DB 冪等 migrate）

- 七張可同步表加 `sync_id`（UUID、unique index）、`version`、`deleted_at`。
- `workouts` 另加 `owner_device_id`／`lease_generation`——同步 payload 帶著它們，
  不存的話 Android 推上來的值會被投影吃掉，pull 回去變成另一個值。
- 既有列 `sync_id` 為 NULL（回填是 F155），第一次被寫到時就地補一顆。

**`app/services/projection.py`（新）——兩層之間唯一的橋**

- `apply_payload()`：sync push → domain row（sync.py 在同一 transaction 內呼叫）
- `record_write()`：REST／Web 改完 domain row → 補版本、寫 `sync_entities` 與 `sync_changes`，
  並推進 `server_seq_high_water`（漏了的話下一次 pull 的回滾偵測會把這些寫入當成序號倒退而停用同步）
- `payload_for()`：domain row → sync payload，形狀以 `app/schemas.py` 的 `Sync*Payload` 為準

**寫入路徑全部改道**：body metrics、daily status、settings、exercises、templates、workouts、sets。
硬刪一律改 tombstone；讀取濾 `deleted_at`；「刪掉再記同一天」＝復活那一列
（`date` 的 UNIQUE 不是 partial index，軟刪的列照樣占位子）。

## 過程中撞到、值得記的三件事

1. **`session.add()` 不能太早**：欄位還沒填完就掛進 session，任何查詢觸發 autoflush 就把半空的
   列送進 DB（`NOT NULL constraint failed: sets.workout_id`）。改成解析完引用、填完欄位才 add。
2. **自然鍵撞號是真的設計問題，不是 bug**：三筆同日體重、同名動作——domain 表的 UNIQUE 讓它們
   不可能共存。決定退成 `natural_key_conflict` 交給 F145 的收件匣，不自動合併也不覆蓋；
   既有 `sync_id` 為 NULL 的列（種子動作、REST 建的）則由推上來的那筆認領。
   受影響的既有測試改成用不同日期——它原本要驗的是分頁，不是合併語意。
3. **軟刪讓 SQLite 不再重用課表 id**，早期那條「刪了再建會繼承歷史」的 bug 從根上消失。
   兩支對應測試改成釘住新語意（id 不重用 ＋ 新課表看不到舊歷史），沒有刪掉觀察面的斷言。

## 範圍

- **既有資料回填不在本條**（F155）：合一之後**新寫入**兩邊統一，合一之前的舊資料仍是兩個世界。
- legacy 單機 token 路徑走 pre-cutover DB，不參與同步，行為不變。
