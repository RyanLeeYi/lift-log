# F154 — domain 表與同步層合一

實作日：2026-08-14。決策依據：vault `DECISIONS.md` **D17**（Ryan 於 grill 十題裁決 Q1／Q6／Q8～Q10）。

## 問題（做 F146 時查出來的）

`app/services/sync.py` 從頭到尾沒碰過 domain models，domain 表也沒有 `sync_id`／`version`。
同一個 user 的 data DB 裡是**兩份互不相干的資料**：Android 同步上來的在 `sync_entities`，
REST／MCP 讀寫的在 domain 表。手機記的組網頁查不到，網頁記的手機同步不到——而兩邊各自的
單元測試都會過。PRD R5／R6 早就寫了「同一份 change log」「不得有繞過同步版本的第二條寫入路徑」。

## 做了什麼

**schema**（`DOMAIN_SCHEMA_VERSION` 3 → 4，既有 DB 冪等 migrate）

- 七張可同步表加 `sync_id`（UUID、unique index）、`version`、`deleted_at`。
- `workouts` 另加 `owner_device_id`／`lease_generation`——同步 payload 帶著它們，
  不存的話 Android 推上來的值會被投影吃掉，pull 回去變成另一個值。
- 既有列 `sync_id` 為 NULL（回填是 F155），第一次被寫到時就地補一顆。

**`app/services/projection.py`（新）——兩層之間唯一的橋**

- `apply_payload()`：sync push → domain row（sync.py 在同一 transaction 內呼叫）
- `record_write()`：REST／Web 改完 domain row → 補版本、寫 `sync_entities` 與 `sync_changes`，
  並推進 `server_seq_high_water`（漏了的話下一次 pull 的回滾偵測會把這些寫入當成序號倒退而停用同步）
- `payload_for()`：domain row → sync payload，形狀以 `app/schemas.py` 的 `Sync*Payload` 為準

**寫入路徑全部改道**：body metrics、daily status、settings、exercises、templates、workouts、sets。
硬刪一律改 tombstone；讀取濾 `deleted_at`；「刪掉再記同一天」＝復活那一列
（`date` 的 UNIQUE 不是 partial index，軟刪的列照樣占位子）。

## 過程中撞到、值得記的三件事

1. **`session.add()` 不能太早**：欄位還沒填完就掛進 session，任何查詢觸發 autoflush 就把半空的
   列送進 DB（`NOT NULL constraint failed: sets.workout_id`）。改成解析完引用、填完欄位才 add。
2. **自然鍵撞號是真的設計問題，不是 bug**：三筆同日體重、同名動作——domain 表的 UNIQUE 讓它們
   不可能共存。決定退成 `natural_key_conflict` 交給 F145 的收件匣，不自動合併也不覆蓋；
   既有 `sync_id` 為 NULL 的列（種子動作、REST 建的）則由推上來的那筆認領。
   受影響的既有測試改成用不同日期——它原本要驗的是分頁，不是合併語意。
3. **軟刪讓 SQLite 不再重用課表 id**，早期那條「刪了再建會繼承歷史」的 bug 從根上消失。
   兩支對應測試改成釘住新語意（id 不重用 ＋ 新課表看不到舊歷史），沒有刪掉觀察面的斷言。

## 第一次驗收抓到的 fail（已修）

獨立驗收判 ③ **fail**：`app/seed.py::seed_exercises()` 直接寫 domain 表、**不經
`projection.record_write()`**——正是 acceptance ③ 與 PRD R6 禁止的「繞過同步版本的第二條
server 寫入路徑」。

實際影響：每個新 Google 帳號建 data DB 時寫進去的 **35 筆種子動作只存在於伺服器的 domain 表**，
`sync_changes` 一筆都沒有，該帳號的手機**永遠 pull 不到預設動作庫**。

為什麼既有測試抓不到：`tests/test_seed_and_static.py` 只驗「種子動作有沒有建起來」，
跨路徑測試只驗自己寫入的資料，**沒有人交叉看「新帳號 seed → pull」這條路徑**。

修法：`seed_exercises()` 每建一筆就 `record_write`。連帶效應——種子動作現在會產生 35 筆 change，
`server_seq` 不再從 1 起算，`tests/test_sync.py` 中寫死絕對序號的斷言改成**相對於登入後的基準游標**
（那本來就是它們真正要釘的東西）。回歸測試
`test_seeded_exercise_library_reaches_the_first_sync` 已補上。

## 第二次驗收抓到的 fail（已修）——同一種漏法，範圍更大

重驗時驗收者又抓到一個：`_log_workout`（`POST /api/workouts/batch`，**也是 MCP `log_workout`
工具的唯一寫入入口**）寫的組**全部沒進 change log**。

根因是我自己寫的那段：先 `session.flush()` 再用 `for written in session.new | session.dirty`
反查剛寫的列——**flush 已經把它們移出 `session.new`**，迴圈永遠掃不到，於是整批組靜默漏掉。
`create_missing` 自動補建的動作同理。workout 本身有進，因為它是明確呼叫 `record_write`。

影響比 seed 那個更大：透過 AI 對話（MCP）記的訓練完全同步不到手機，而那正是這個專案的主打。

修法：**明確收集寫了哪些列**（`written_sets` list），不靠 session 的集合狀態；
`create_missing` 建動作的當下就 `record_write`。回歸測試
`test_batch_and_mcp_writes_reach_the_change_log` 已補上。

**自己補掃**：`grep session.add(` 全 repo，11 個 domain 寫入點逐一核對都有 `record_write`
（`TemplateExercise` 是課表 payload 的子項，隨父層一起送，不需要自己的 change）。

## 第三次驗收抓到的 fail（已修）——raw SQL 是 grep 的死角

`delete_template()` 用一句 bulk `UPDATE workouts SET template_id=NULL` 解除關聯。那也是
domain 寫入，但它繞過 ORM，因此也繞過 change log：被清掉關聯的 workout 在同步層**停在
「課表還在」的舊版本、版本也沒往上**，另一台裝置永遠看不到這次變更（違反 acceptance ②④）。

**方法論教訓**：我上一輪自己補掃時用的是 `grep session.add(`——那抓不到 `session.execute(update(...))`
這類直接發 SQL 的寫入。驗收者改用 `session.execute(update(` / `.execute(delete(` 才抓到。
往後查同類問題要兩種都掃。

修法：改成逐筆取出、逐筆改、逐筆 `record_write`。回歸測試
`test_deleting_a_template_syncs_the_workouts_it_detaches` 已補上。
