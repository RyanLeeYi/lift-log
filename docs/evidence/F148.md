## 為什麼這樣做（授權範圍內的判斷與取捨）

- **Backup retention 的實作方式**：規格建議「control DB 留刪帳 tombstone +
  retention 到期時間，restore/啟動流程遇到 tombstone 一律拒絕還原為 active」——
  照建議原樣做，沒有另外蓋備份系統。`purge_after` 目前只是存著，沒有任何程式碼
  讀它做「到期後允許復原」的判斷（刪除是永久的，不會到期後變成可還原）；它是留給
  未來一支尚未存在的 backup 清除排程用的到期時間戳，屬性上是「營運排程的輸入」不是
  「業務邏輯的分支條件」。
- **`User` 列保留、只標 `closed`，不硬刪**：硬刪會讓 `AccountTombstone` 的
  FK 失去參照對象，也會讓 `google_sub` UNIQUE 約束跟著消失——同一個 Google 帳號
  馬上就能用登入流程重新註冊、拿到一個全新空帳號（這其實不是壞事，是刪帳後
  重新開始的合理路徑），但那樣就沒有東西擋著「用同一顆已撤銷的 refresh token
  或已知 google_sub 硬湊出來的請求去摸到舊資料」。保留列＋`status="closed"`是
  `login_with_google` 既有邏輯（`status != "active"` 即拒絕）現成就會擋下的最小
  改法，不必新增判斷分支。
- **Reauth 用「每次請求都帶一顆新鮮 id_token+nonce」而非「建一個有效期的 reauth
  grant」**：PRD 只要求「近期重新驗證」，沒有要求跨請求的 grant 概念；Google
  ID token 本身的 `exp`＋前端每次重新觸發 Credential Manager／GSI prompt 產生的
  新 nonce，天然就是「這一次動作前剛做過的身分驗證」，不必另外在 control DB
  存一個 reauth 時間戳、也不必決定 grant 的有效期窗口這種本來不存在的新參數。
  代價：每次匯出或刪帳都要重新跳一次 Google 驗證 UI，比「登入後 5 分鐘內免重驗」
  的 UX 重一點，但換來零額外狀態、零新設定值。
- **匯出直接重用既有 REST 回應 Pydantic model（`ExerciseOut`／`WorkoutOut`／...）
  而非另建一份匯出專用 schema**：這些形狀已經是「對外公開、稽核過不含憑證」的
  欄位集合（本來就是 REST API 在吐的東西），重用它們同時滿足「不含 access/refresh
  token、MCP token hash、Google token、server 路徑」——不是我在維護第二份欄位
  白名單去保證這件事，是既有 REST 契約已經保證這件事。
- **Delete 端點的 rate limit 順序放在 reauth 驗證之前**：與 `/api/auth/google`
  既有的 `_rate_limit` 順序一致（先擋次數，再花成本去打 Google 驗證），也代表
  reauth 失敗（打錯 nonce）仍計入 3/hour 額度——`tests/test_account.py::
  test_delete_account_rate_limited_at_three_per_hour` 因此改用「連續打錯 nonce
  逼近限流」而非連續真刪除（帳號刪一次憑證就失效，打不出第二次）。
- **登出端點沒有新增**：`/api/auth/logout` 的 `resolve_session` 本來就同時接受
  `access_token`（android）與 `web_cookie`，CSRF 檢查只在偵測到 cookie 時才要求，
  native 沒有 cookie 天然跳過——這支端點對 native 已經是可用的，加一支新端點只是
  重複邏輯。
- **Web 端沒有加 pending/conflict 登出攔截**：F148 acceptance 原文只寫「Android
  有 pending mutation/conflict 時」，且 web 目前沒有等同 Android outbox 的本機
  離線佇列（F146 evidence 記錄的懸而未決規格問題：Web 端 IndexedDB 離線佇列是否
  該做），照字面與現況都不該幫 web 加這個攔截，避免超出凍結 acceptance 去猜一個
  還沒裁決的機制。

## non_goals 對應

- 「不在未處理 pending/conflict 時靜默清本地資料」：`nativeSignOutRow` 一律先讀
  `readNativeSyncStatus()`，`pending>0 || conflicts>0` 時攔下彈窗，不直接呼叫
  `finishNativeSignOut()`。
- 「不讓備份刪除繞過 retention 紀錄」：本輪沒有實作任何「刪除備份」的程式碼路徑
  （`ACCOUNT_DELETE_RETENTION` 只在寫入 tombstone 時用一次），沒有東西可以繞過。

## 延後或卡點（未逾越授權，記錄供驗收與後續參考）

- **Android 登出攔截視窗（`logoutBlockedModal`）沒有 Playwright／JS 單元測試直接
  斷言「pending>0 時真的彈窗、三個按鈕各自行為正確」**。`verify_f148.py` 只測了
  web 路徑的匯出／刪帳（native-only 的 `nativeSignOutRow` 在瀏覽器環境
  `isNativeApp()` 恆為 false，走不到）。這段邏輯在 `account.js` 裡很薄（純讀
  `readNativeSyncStatus()` 回傳值做分支），且 Android 沒有無頭瀏覽器可跑
  WebView 集成測試，是本輪認為性價比最低、風險也最低的缺口（分支邏輯本身在
  `LocalStore`／`native-sync.js` 層都有覆蓋，account.js 只是接線）。如果驗收
  認為這段必須有自動化證據，需要新增一支能注入 `isNativeApp()=true`＋假
  `globalThis.Capacitor.Plugins` 的瀏覽器測試（目前專案沒有這種 harness）。
- **`api.wipeLocalData()` 在刪帳流程中被呼叫**這件事，只在程式碼閱讀層級確認
  （`account.js::finishDeleteAccount`），沒有獨立測試斷言「刪帳後 native 一定會
  呼叫到 wipe」——理由同上，需要能模擬 native 環境的瀏覽器測試才測得到。
- 沿用 F146/F147 遺留的兩個規格層級待裁決事項（見 `docs/evidence/F146.md`
  末段）：legacy 單一 token 路徑要不要收掉、Web 端 IndexedDB 離線佇列的非目標
  字面出入。F148 的行為沒有依賴這兩個裁決結果，維持原樣。
- `verify_f48.py` 的版號同步檢查是既有債務（見上），未在本輪修正。
