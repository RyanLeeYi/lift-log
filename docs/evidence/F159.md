## 逐條對照

### ① 根因：pull 路徑用 `getInt` 讀 nullable 欄位

`LocalStore.java::applyRemoteUpsert()` 的 `case "set"` 原本是
`values.put("reps", payload.getInt("reps"))`。org.json 的 `getInt` 對 `JSONObject.NULL` 一律拋
`JSONException`——而同一段的 `rpe`／`rest_seconds` 一直是用 null-safe 的
`putJsonNullableInteger`。改成 `reps`／`duration_seconds` 同待遇。

`case "exercise"` 的 `mode` 用 `payload.isNull("mode") ? "reps" : payload.getString("mode")`。
org.json 的 `isNull` 對「key 不存在」與「值是 NULL」回同一結果，所以舊 server payload
（完全不帶 `mode`）也安全。

### ② 放大原因：整批回滾 ＋ cursor 卡死

`applyPullPage()` 的 change apply 與 cursor commit 共用同一個 transaction（該檔既有註解與既有測試
`pullPageAndCursorCommitTogether` 都證實這是刻意設計），`SyncClient.syncOnce()` 的 pull 迴圈沒有
per-change try/catch。所以後果不是「時間型的組存不進去」，而是**該裝置的 pull cursor 永久卡在那一頁
之前**，連同頁之後所有正常的次數型資料一起擋住，且不會自我恢復。

`SyncClient.java` 本次**未改動**——acceptance 要求的是「時間型 set 不再觸發這個放大後果」，
不是改掉 transaction 設計。

### ③ schema：整表重建

`DATABASE_VERSION` 3 → 4。`migrateVersion4()` 兩步：

1. `exercises` 用 `ALTER TABLE ADD COLUMN mode TEXT NOT NULL DEFAULT 'reps'`
2. `sets` 整表重建（SQLite 沒有 ALTER COLUMN）：`reps` 從 `NOT NULL CHECK(reps > 0)` 放寬成
   `CHECK(reps IS NULL OR reps > 0)`，新增 `duration_seconds`

重建後的表與原 `createVersion1Schema` 的 `sets` 逐欄核對：欄位、CHECK、兩條 FOREIGN KEY、
`syncColumns()`、唯一索引 `ux_sets_number_active`（含 `WHERE deleted_at IS NULL`）全部相同，
無漏無增。重建前後比對**複製保真度指紋**（筆數、相異 client_uuid／workout_sync_id／
exercise_sync_id 數、reps／set_number 加總、weight_kg 換成分後加總），不吻合就
`throw IllegalStateException`；另有 reps-not-null 反查作第二道。

`weight_kg` 指紋刻意 `CAST(ROUND(SUM * 100) AS INTEGER)`——浮點數直接比較會偽陽性。

**不關 `PRAGMA foreign_keys`**（server 端要關）：`SQLiteOpenHelper` 的 onCreate／onUpgrade 本來就
整個包在一個 transaction 裡，PRAGMA 在交易內無效；而且不需要——`sets` 只有指出去的 FK，
沒有其他表以 FK 指向它。

### ④ migration 呼叫順序：v4 先於 v3

`onCreate` 與 `onUpgrade` 都是 `v1 → v2 → v4 → v3`。

理由：`migrateVersion3` 的 `enqueueExistingDomainRows()` 共用 `exercisePayload`／`setPayload`，
而這兩個函式現在會讀 v4 才新增的 `mode`／`duration_seconds`。照版本號順序跑的話，
v1／v2 裝置升到 v4 會在 v3 的 backfill 階段撞 `no such column: mode`。

換序安全的前提：`migrateVersion4` 只碰 `exercises`／`sets`，不依賴 v2／v3 建的表。
**這是既有測試先紅才抓到的**（`versionOneUpgradePreservesDomainRows`、
`versionTwoUpgradeBackfillsEveryExistingDomainRow`），不是事後推測的風險。

### ⑤ 離線寫入路徑

`LocalStorePlugin.addSet/updateSet` 的 `reps`／`durationSeconds` 都改成 `optionalInt`，
新增 `validateSetMode()` 擋「兩個都給／兩個都沒給／非正數」。`createExercise` 新增
`requireMode()`（值域 `reps`／`time`，省略＝`reps`）。

**橋接兩端的鍵名逐字核對過**（這是最可能靜默丟資料的地方，也正是 F105 那條 P0 的形狀）：
`app/static/js/api.js:359-371` 送 `durationSeconds`（來源 `payload.duration_seconds`），
Plugin 讀的是同一個字。`mode` 同理（`api.js:332`）。

Android 端**沒有**重現 server 的 `assert_set_matches_mode`（依動作實際 mode 交叉驗證），
只做「擇一且正數」的格式驗證——server 端本身也沒有這道 DB CHECK，互斥判斷在 service 層，
而 JS `localApi` 已依動作 mode 決定送哪個欄位。多做交叉驗證是範圍外的加固。

### ⑥ 回歸測試

`LocalStoreTest.java` 原本對 `entity_type="set"` 的 pull 情境**零覆蓋**。新增三條：

1. `pullAppliesTimedAndCountedSetsInSamePageWithoutException`——一頁內含時間型 set
   （`reps=JSONObject.NULL, duration_seconds=60`）＋其後次數型 set，斷言不拋例外、
   `serverCursor()` 前進到 3、兩筆都落地
2. v3→v4 遷移保留既有次數型資料且可重跑兩次（冪等）
3. `addSet`／`updateSet` 離線寫入時間型資料

**紅→綠證據**：把 `case "set"` 的讀法暫時還原成 `payload.getInt("reps")`，第 1 條立刻
`JSONException` 失敗；改回 `putJsonNullableInteger` 後 20/20 綠。獨立驗收者也自己重跑過一次
這個還原實驗，確認不是空測試。

### ⑦ 不回歸

`addSet`／`createExercise` 保留舊簽章當**薄殼委派**到新簽章（不是第二份邏輯）——

### P2：原生浮動視窗的快記寫錯欄位

**本次引入、且不可自我恢復**，所以不適用 DEFER。

失敗情境（自己重跑證據鏈確認過，不是照抄報告）：使用者在網頁建一個時間型動作
（例：棒式）→ 同步到手機 → 開始休息 → 按浮動視窗的「完成這組」。

- `app.js` 兩處組 draft 的地方送的是 `reps: state.reps`
- 但時間型動作的 `state.reps` 裝的是**秒數**（`app.js` 約 :2520 在 API 邊界才轉成
  `duration_seconds`）
- `RestOverlay` 收到後走 11 參數的 `addSet`，秒數落進 `reps` 欄、`duration_seconds` 留 NULL
- push 上去被 `app/services/projection.py::assert_set_matches_mode` 回 **422**，
  那筆 outbox mutation 永遠送不出去

F159 之前時間型動作在 Android 本地根本存不了，所以這條路不可達——**是 F159 讓它變成可達的**。

修法（Ryan 在兩個選項中選了完整支援，而非「時間型不給快記」）：draft 多帶 `mode`
（值域 `reps`／`time`），一路貫通 `app.js` → `native-notify.js` → `RestTimerPlugin`
→ `RestTimerService`（新增 `EXTRA_MODE`）→ `RestOverlay`。

| | 標籤 | 步進 | 寫入 |
|---|---|---|---|
| 次數型 | `N 次` | ±1 | `reps=N` |
| 時間型 | `N 秒` | ±5 | `duration_seconds=N`、`reps=null` |

**向下相容**：四層各自獨立退回 `"reps"`（JS 的 `?? "reps"`、`call.getString` 回 null、
intent 預設、`"time".equals(mode)`），任一層被舊版跳過都不影響其他層；舊版 APK 收到
沒有 `EXTRA_MODE` 的 intent 也落在同一個預設分支。

`adjustDraft` 的 `dr` 參數語意由「delta」改成「方向」，步進量在函式內依 mode 決定。
四個呼叫端逐一核對過只傳 ±1／±2.5，重量那兩顆不受影響。

### P3-1：DB 層的互斥護欄

重建的 `sets` 加 `CHECK((reps IS NULL) <> (duration_seconds IS NULL))`。
既有資料必過（v1–v3 的 `reps` 一律 NOT NULL、`duration_seconds` 重建時填 NULL）。

**它擋不到上面那個 P2**——秒數寫進 `reps` 欄時型別完全合法，只是語意錯。
互斥判斷仍在 service 層與 `LocalStorePlugin::validateSetMode`。

實作上踩到一個 SQLite 語法規則：**表級約束必須排在所有欄位定義之後**，
插在欄位中間會 `near "rpe": syntax error`（29/36 測試直接紅）。

### P3-2：指紋涵蓋率

原本 14 個欄位只涵蓋 4 個，把 `deleted_at` 與 `created_at` 對調會完全通過檢查——
而那正是它宣稱要擋的那類故障。新增 `rpe`／`rest_seconds`／`version` 加總與三個時間戳的
相異值數量。

限制要講清楚：**純聚合統計量對「值分佈對稱的兩欄互換」天生看不出來**，
這是該檢測手法的極限，不是實作疏漏。回歸測試刻意讓兩筆 set 的 `deleted_at` 相同、
`created_at` 不同，才驗得出差異。

### P3-3：冪等依據

`rebuildSetsForNullableReps` 從 `!setsRepsIsNotNull(db)` 改成
`hasColumn(db, "sets", "duration_seconds")`——後者才是「已經重建過」的直接證據；
前者只是重建的其中一個結果，日後再放寬別的欄位就會誤判。
重建後的 `setsRepsIsNotNull` 反查保留為第二道。

## Rollback

**裝置端的 schema 重建不可逆，而且降版會被明確擋下。**

`LocalStore.onDowngrade()` 是既有設計，直接
`throw IllegalStateException("禁止 LocalStore schema 降版")`（不是靜默毀損）。
所以：

1. **一旦某台裝置裝了含 F159 的 APK，就不能再退回舊 APK**——舊版的
   `DATABASE_VERSION = 3` 開不了已經是 v4 的本地 DB
2. 真要退版只能「解除安裝再裝舊版」，代價是**清掉該裝置的本地 DB 與尚未送出的 outbox**。
   所以退版前要先確認該裝置的 outbox 已清空（同步成功）
3. 伺服器端不受影響——F159 沒有動 server，退 APK 不需要退 server
