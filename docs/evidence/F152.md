# F152 — 批次寫入 dry-run 摘要

驗收日：2026-08-13。

`POST /api/workouts/batch` 支援 `dry_run: true` → 回 **200**（不是 201）與
`will_create_count`／`will_skip_count`／`will_conflict_count`，外加前 5 筆 `preview`。

- 判斷邏輯抽成 `_plan_batch`，dry-run 與實際寫入**共用同一份**，沒有第二套規則。
- `preview` 筆數 = `min(len(sets), 5)`，恰為原 payload 的 index `0..N-1`（N=8 截斷成 5、
  N=2 回 2、N=1 回 1，皆逐筆比對 `weight_kg` 相符）。
- dry-run 零副作用：前後 `exercises`／`workouts`／`sets` row count 不變；`SyncChange`
  為 0 筆、`server_seq_high_water` 不變。`session.rollback()` 放 `try/finally`，
  `create_missing` 拋例外時也不留 Exercise 列。
- 同批先 dry-run 再實際寫入結果一致：`will_create_count=3` = `created_count=3`；
  寫入後重跑 dry-run 轉為 `will_skip_count=3`／`will_create_count=0`。
- `conflict` ＝ idem_key 沒命中但目標 workout 已有同 `(exercise_id, set_number)` 未刪組
  （來源是 F151 之前、`idem_key` 為 NULL 的舊資料），由既有測試
  `tests/test_batch_dry_run.py::test_conflict_from_legacy_null_idem_key_row` 覆蓋。
