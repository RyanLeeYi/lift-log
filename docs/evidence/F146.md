## 做了什麼

**server**

- 既有（F142 時期）：Secure / HttpOnly / SameSite=lax cookie、CSRF 比對、domain API 綁 session
  user、登出撤 session、cookie 不能當 Bearer 重放。CORS 是固定白名單且沒開 credentials，
  所以 CSRF token 不會被跨站讀走。
- 新增：**CSRF token 改由 `hmac(LIFTLOG_TOKEN, session_id)` 推導**，`GET /api/auth/session`
  對 web session 回傳它。原本是隨機值只存 hash——回應送出去就再也拿不回來，網頁一重整
  cookie 還在、token 沒了，**所有寫入 403**。
  第一版寫成「每次讀 session 就換一顆」，當場打爆既有的 logout 測試（換發＝讓對方手上那顆
  失效），才改成推導值。Android session 不發 CSRF token，有測試釘住。

**前端**

- `auth.js`：`restoreWebSession` / `signInWithGoogleWeb` / `signOutWeb` / `getWebCsrfToken`。
  網頁不存 access token，只留 CSRF token；GSI script 在按下登入時才動態載入（不進 index.html，
  APK 因此不會多一個外部相依）。**503 不當成未登入**——那會把服務中斷畫成「請重新登入」。
- `api.js` `authHeaders()`：有 web session 走 cookie＋`X-CSRF-Token`；沒有才退回舊的 Bearer。
  兩條路併存是刻意的，理由見下。
- setup 畫面：Google 登入為主要動作，API token 欄位留作備援；設定頁加登出。
- 開站時登入服務不可用 → 專用的離線訊息。**不能用 `state.error`**：頂層的
  `guard(confirmActiveWorkout)` 會在啟動時把它清成 null，訊息會憑空消失（實測踩到）。

## 為什麼保留舊的 API token 路徑

acceptance 要求「現有 Web 行為不回歸」。舊的單一 token 是 **60+ 支既有 e2e 的入口**，
server 端也還留著 legacy 判定（`app/api/deps.py::_is_legacy_request`）。直接砍掉等於一次
廢掉所有既有 Web 回歸驗證。**這是我的判斷，需要 Ryan 確認**：如果公開版要求「只能 Google
登入」，那要另外排一條 feature 把 legacy 路徑與相關 e2e 一起收掉。
