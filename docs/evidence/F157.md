# F157 web session 到期不再是硬斷線

## 問題來源

追 F156（手機 app 被自己的背景同步登出）時查到的另一半：`WEB_SESSION_TTL = timedelta(hours=12)`，而 web 登入不發 refresh token（`issue_session` 只有 `client == "android"` 才發）。所以 web session 是**固定 12 小時硬到期、不隨使用延長、也沒有續期途徑**——網頁上連續使用的人照樣被踢回登入畫面。

## 修法

滑動到期 + 絕對上限，兩層都要推：

1. **DB 層**（`app/services/auth.py::resolve_session`）——沿用既有的 `last_seen_at` 寫入點，把 `access_expires_at` 推成 `min(now + WEB_SESSION_TTL, created_at + REFRESH_ABSOLUTE_TTL)`。用 `min()` 夾制，所以「一直有請求進來」也推不過 90 天。
2. **Cookie 層**（`app/api/deps.py::issue_web_session_cookie`）——Max-Age 由 `access_expires_at` 反推，不獨立計算。兩邊永遠一致，絕對上限自動生效。

絕對上限沿用 `REFRESH_ABSOLUTE_TTL`（90 天），跟 Android refresh token family 同一個「多久不重新驗證身分就得重新登入」政策，不為 web 另開平行常數。

### 收斂成單一路徑

`resolve_session` 原本有三個各自獨立的呼叫入口。cookie 續發**不**掛在各入口上，而是：

- `app/api/deps.py::resolve_request_session()` 成為唯一的 session 解析入口，只在 `request.state` 登記待續發的 cookie
- `app/main.py::slide_web_session_cookie` middleware 統一寫進回應

放在 middleware 而非 dependency，是為了涵蓋錯誤回應：CSRF 403 與 rate limit 429 拒絕的是「這一次請求」，不是「這個 session」，不該因為打錯一次就讓登入狀態開始倒數。401（session 真的無效）則在 `resolve_request_session` 就 raise，走不到登記那段，所以不會續發。

順手刪掉 `app/api/auth.py` 與 `app/api/account.py` 各一份因此變成死碼的 `_bearer()`。

## 驗收（acceptance-verifier，fresh context，三輪）

**前兩輪都 fail，擋下的是同一種缺陷的兩個層次。**

| 輪次 | 判定 | 擋下什麼 |
|---|---|---|
| 1 | R1 fail | DB 的到期有滑動，但 cookie 的 Max-Age 只在登入當下設一次。瀏覽器到期就丟掉 cookie、之後不再送出，滑動在真實瀏覽器裡**從未生效**——症狀完全沒被修掉，而測試是綠的（只斷言 DB 欄位）。 |
| 2 | R1 fail | 修正版把 cookie 續發**逐個呼叫點補**，補了兩個、漏掉第三個（`app/api/account.py::_current`，即 `/api/account/export`、`/api/account/delete`，web 前端確實會呼叫）。驗收者的結構性建議：收斂到單一必經點，否則往後每新增一條直接呼叫 `resolve_session` 的路由就複製一份同樣的洞。 |
| 3 | **6/6 pass** | — |

第三輪驗收者自行 grep 全 repo 的 `resolve_session` 呼叫點（確認只剩 `resolve_request_session` 與 Android bearer-only 的 `require_app_download_auth`）、確認 mount 的路由仍經過頂層 middleware、並用 TestClient 交叉驗證五種情境：一般路由、`/api/account/export`、CSRF 403、rate limit 429、session 過期 401。另外自行測了「`created_at` 剛好等於 90 天前」的邊界（回 401，無 off-by-one）。

## 教訓

**「DB 記錄了」不等於「客戶端知道了」。** 到期時間在兩邊各有一份、各自執行，只推伺服器那份是看不見的。前兩輪的 fail 是同一個錯誤的兩個層次：第一次是漏了整個 cookie 層，第二次是修對了層次但補在錯誤的粒度上——逐個呼叫點補，等於把正確性寄託在「下一個人記得」。

## 實際 touches

規格的 `touches` 只列了 `app/services/auth.py`、`app/api/deps.py`、`tests/`。實作為了收斂成單一路徑，另外動了 `app/api/auth.py`、`app/api/account.py`、`app/main.py`——擴大範圍是驗收第二輪的結構性建議促成的，不是 scope drift。
