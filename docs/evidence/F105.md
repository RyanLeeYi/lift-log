# F105 時間型動作 — 證據

日期：2026-08-19。檔位 `strict`（動到資料模型與 migration，不可逆）。

## 做法概要

一條 feature 切成五塊：後端契約（主 session）＋四個平行 worktree worker（各自獨佔檔案）＋
主 session 補四者之間的縫。commit：`d07b3e1`（後端）、`26283b8`／`3072496`（簽核與 touches）、
`c499678`（前端與整合）。

## 逐條對照

### ① 資料模型

- `exercises.mode`（`'reps'` 預設／`'time'`）、`sets.duration_seconds`（nullable int）
- `sets.reps` 改為 nullable。**SQLite 沒有 ALTER COLUMN**，所以 `app/migrations.py` 的
  `_rebuild_sets_for_nullable_reps()` 走整表重建：建新表 → `INSERT ... SELECT` → drop → rename →
  補回 6 個索引（含兩個 partial unique）。走 DBAPI 原生連線並自己下 BEGIN/COMMIT，因為
  `PRAGMA foreign_keys` 在交易內是無效指令而 SQLAlchemy 2.0 一 execute 就 autobegin
- 既有資料全部視為 `'reps'`（`ALTER TABLE ... ADD COLUMN mode TEXT NOT NULL DEFAULT 'reps'`）
- `DOMAIN_SCHEMA_VERSION` 4 → 5，版本戳最後才寫（中途失敗要停在舊值）

**對真實正式 DB 的副本實測**（`prod-data/users/68ea7b49-….db`，150 筆 sets）：

```
rows: 150 -> 150
sums(reps, weight_kg): (1238, 6645.0) -> (1238, 6645.0)
indexes preserved: True
reps notnull: 0 | duration_seconds: True
exercises.mode: [('reps', 40)]
schema_version: ('5',)  fk_check: []
idempotent rows: 150   idempotent indexes: True
null-reps insert: (None, 60)
```

重建前後比對「複製保真度指紋」（筆數、相異 client_uuid 數、reps／weight_kg／set_number／
workout_id 加總），不一致就 rollback。**刻意不用 `PRAGMA foreign_key_check`**：F151 之前的舊表
沒有 FK 子句，重建後才有，既有孤兒列會在重建後「首次」被報出來、看起來像是這次弄壞的
（`tests/test_migration.py` 的 legacy fixture 就是這種形狀，實測踩到）。

`created_at` 在重建後的新表**不加 NOT NULL**（雖然 create_all 對新 DB 會加）——舊表允許 NULL
且真的有這種列，重建不該比它取代的那張表更嚴格，否則升級會炸在 `INSERT ... SELECT`，
而唯一的「修法」是替使用者捏一個假的建立時間。

### ② 寫入驗證

`app/services/exercises.py::assert_set_matches_mode()` 是唯一定義點，**三條寫入路徑共用**：
REST（`log_set`／`update_set`）、MCP（`log_workout` 的 `_plan_batch`）、同步 push
（`projection.apply_payload`）。四種壞組合都擋：時間型帶 reps、次數型帶 duration_seconds、
兩個都帶、兩個都不帶。

狀態碼 **422**（`UnprocessableError`）。⚠ 這個 repo 原本把 pydantic 驗證錯誤一律翻成 400，
acceptance ② 明寫 422，所以新增了一個只給「欄位組合與 mode 不符」用的例外類。
連帶影響：次數型動作漏帶 reps 從 400 變成 422（`tests/test_api_workouts.py` 已更名反映）。
**這是本條唯一對既有行為的改變。**

### ③ 時間型不進噸位

`set_tonnage()` 在 `reps is None` 時回 `0.0`，不做任何秒數折算。
`LogWorkoutSummary`、`CalendarDay`、`LastWorkout` 各自多一個 `duration_seconds`，與噸位**並列**。
首頁「上次訓練」卡在 `duration_seconds > 0` 時多一格（`['500', '90']` / `['kg', '秒']`，
E2E 直接驗兩個值不相等、沒有被加成一個）。
`schedule.py` 的噸位查詢不必加條件——SQL 的 `weight * NULL` 是 NULL，`SUM` 略過 NULL。

### ④ 熱力圖改吃組數

`GET /api/stats/calendar` 的 `days` 從「日期 → 數字」改成
「日期 → `{tonnage_kg, duration_seconds, sets_count}`」。
`calendar.js::level()` 改用固定門檻 ≤3／≤7／≤13／>13（不再是「同月內比噸位」的相對值）。
`verify_f85.py` 的種子與 5 條分級斷言同步更新（原本每天只記 1 組、靠噸位分級）。

### ⑤ 時間型的 PR 是兩張卡

`history.py` 依 mode 分流成 `_time_prs()` / `_reps_prs()`。時間型回
`top_set_duration` 與 `top_session_duration_seconds`，其餘四項（含 `top_est_1rm`）**全部 None**。
前端 `exercise-detail.js` 對時間型只產出兩張卡——**估計 1RM 的節點不存在於 DOM**，不是顯示 `—`。
E2E 數節點數量與量測寬度（175px/175px 等分）。

### ⑥ logger／顯示／自訂動作

- logger 依 mode 換 stepper（`REPS ±1` → `秒數 ±5`），沿用 F102 直接輸入，**沒有做碼表**（⑧）
- 組列表、日曆明細、動作詳情頁一律「60 秒」而非「60 次」
- 自訂動作建立視窗多一個「時間型動作（記秒數，如棒式）」勾選框（`custom-exercise.js`）
- **`TemplateExerciseOut` 增加 `mode`**：少了它，每個從課表進入的寫入路徑（今日菜單、接著做、
  日曆批次補記）都得各自反查動作的 mode，漏掉的那個就會送出 reps 並吃 422。改在共用契約上一次修好

### ⑦ MCP

`get_progress` 對時間型回**最長那組**的 `duration_seconds`（拿時間型去比 `weight_kg` 只會得到
一條全 0 的線）。`query_workouts` 每組多回 `duration_seconds`。`log_workout` 的 docstring
說明兩者擇一、tonnage 與 duration 並列不相加。

## Rollback

Migration 是**不可逆**的（整表重建）。回退步驟：

1. 部署前先做 DB 快照：`VACUUM INTO` 到 `prod-data/users/<id>.f105-pre.db`
   （同 `scripts/backfill_sync.py` F155 的作法）
2. 要回退就停服務、把快照複製回原檔名、`git checkout <前一個 commit>` 後重新 `deploy.ps1`
3. **不要**只 revert 程式碼而留著已重建的 sets 表——舊 code 對 nullable reps 沒有防護

## 獨立驗收擋下的 P0（已修）

2026-08-19 第一輪 `acceptance-verifier` 判 ⑨ **FAIL / P0**，主 session 判定 `FIX`（P0 只能 FIX）。

**問題**：`assert_set_matches_mode` 拋的 `UnprocessableError` 不是 `ValueError` 家族，而
`app/services/sync.py::_process()` 只攔 `(ValidationError, ValueError)`。例外一路穿到 FastAPI
全域 handler → 整個 request 變 422 → `push()` 的 `session.commit()` 跑不到 →
**同一批裡完全合法的 mutation 一起被 rollback**。Android 把 422 當不可重試，
`markPushPermanentFailure` 對整個 mutations 陣列逐筆 `markMutationFailed`，
於是佇列裡無關的體重、狀態、次數型組全部永久失敗、不再自動重試。

**根因**：`sync.py` 不在 F105 的 `touches` 清單，所以四張派工單都沒有涵蓋它——
是派工時的範圍缺漏，不是任何 worker 的錯。

**修正**：`fix(F105)` commit `4b1741e`——兩處 `except` 補上 `UnprocessableError`，
壞的那筆退成 `conflict`，其餘照常寫入。

**回歸檢查**：`tests/test_sync_domain_bridge.py::test_bad_set_mode_does_not_wreck_the_rest_of_the_push_batch`
（先寫成會紅的，修完轉綠）。修正後 `uv run pytest` **462 passed**、F105 五支 E2E 87/87 不變。

## 已知範圍外落差（不屬於本條 acceptance，需另開條目）

1. **`android/app/src/main/java/com/ryanleeyi/liftlog/LocalStore.java` 完全沒有 `mode`／
   `duration_seconds`**，且用 `int reps` 與 `payload.getInt("reps")`。時間型的組 `reps` 是 null，
   `getInt` 會丟 JSONException——**第一筆時間型資料出現時 Android 同步會斷**。
   確切位置是 `applyRemoteUpsert()` 的 `case "set"`：`values.put("reps", payload.getInt("reps"))`。
   同一段的 `rpe`／`rest_seconds` 用的是 `putJsonNullableInteger` helper，`reps` 卻用 `getInt`——
   **這是 pull 路徑**，所以只要伺服器上存在任何一筆時間型組，Android 每次 pull 都會丟
   JSONException、整條同步斷掉。上面那個 sync push 的 P0 修正救不到這條。
   acceptance ⑨ 的逐項檔案清單沒有列 `android/`，所以本條沒有動它，
   但**這是上 APK 前必須解決的事**，需要 Ryan 裁決是擴 F105 範圍還是另開條目。
2. `verify_f92.py` 有 6 條失敗，已用 `800c0e2`（F105 之前）實測確認是**既存問題**，與本條無關。
